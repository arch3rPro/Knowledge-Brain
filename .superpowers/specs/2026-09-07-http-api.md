# HTTP API Design

## Goal

Expose the existing application requests to local applications and future WebUI/GUI clients without duplicating Vault rules. The server is optional, runs inside the `kb` executable, and is never required by CLI or file-based workflows.

## Startup and authority

```text
kb serve [--bind <IP:PORT>] [--token-file <PATH>] [--allow-write] [--vault <PATH_OR_ID>]
```

The default bind is `127.0.0.1:9432`. A non-loopback address is allowed only when the user explicitly passes it and provides a nonempty token file. `--allow-write` also requires a token, including on loopback. The token is read from a file rather than a command argument so it is not exposed in ordinary process listings.

The selected Vault is fixed at startup. Requests cannot supply another Vault path, archive path, configuration directory, or filesystem target. The HTTP process has no broader Vault authority than the equivalent shared `AppRequest` calls.

Loopback read-only mode may run without authentication. When configured, every API route requires `Authorization: Bearer <token>`. The initial server uses plain HTTP; non-loopback use is suitable only on a trusted network or behind a user-managed TLS reverse proxy. It sends no permissive CORS headers.

## API

Paths intentionally have no version prefix. Every success/error body uses the same `schema_version: v1.0` JSON envelope as CLI JSON.

| Method and path | Shared operation | Read-only mode |
| --- | --- | --- |
| `GET /capabilities` | capabilities plus HTTP policy | allowed |
| `GET /status` | selected Vault status | allowed |
| `GET /doctor` | selected Vault diagnostics | allowed |
| `POST /query` | `SearchRequest` | allowed |
| `POST /lint` | Wiki lint | allowed |
| `POST /review` | source review and plan creation | allowed |
| `POST /plans` | `KnowledgePlanRequest` plan creation | allowed |
| `GET /operations/{operation_id}` | operation inspection | allowed |
| `POST /operations/{operation_id}/apply` | apply reviewed operation | only with `--allow-write` |

Review and plan creation may write machine-local operation records but do not change Vault content. Configuration mutation, backup restore, arbitrary file reads, admission edits and migration are not exposed in this first HTTP slice.

JSON request bodies are limited to 1 MiB. Unknown routes and methods return JSON errors. Application errors retain their stable code/message/retry/next-action fields and map to HTTP status without changing domain meaning.

## Runtime and lifecycle

`kb-server` owns HTTP parsing, authentication, routing and status mapping. Each handler constructs a typed `AppRequest` and calls `kb-app`; it never opens Vault files. Blocking application work runs outside async reactor threads. `kb-cli` owns startup argument parsing and starts `kb-server` on a Tokio runtime.

The server prints one startup JSON line containing the resolved bind address, Vault identity, read/write policy and authentication state, then serves until Ctrl-C or process termination. Binding port `0` is allowed for tests and embedding.

SSE is not faked in this slice. Existing operations do not yet publish durable progress events; an SSE endpoint will be added with the operation-event contract rather than emitting meaningless heartbeats or making requests repeat after reconnect.

## Verification boundary

Focused tests cover loopback startup, the JSON envelope, Vault fixation, body limits, authentication, LAN/write-policy rejection, read routes, plan creation, apply denial and explicitly enabled apply. Native Windows/Linux execution, TLS deployment, browser UI, SSE reconnection and denial-of-service hardening remain unverified.
