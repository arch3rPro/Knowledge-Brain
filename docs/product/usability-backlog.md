# 使用体验改进

本文档记录真实 Vault 使用中已经确认、尚未实现的产品体验改进。具体交互语义、兼容边界和 Skill 分发约定见[使用体验与 Agent Skill 套件设计](../superpowers/specs/2026-09-08-usable-agent-skills-design.md)；现有命令、文件格式和安全边界仍以 reference 与架构文档为准。

## 目标原则

- 机器身份保持精确、稳定；人类界面优先展示易识别的信息。
- 查询、检查和生成预览等只读操作不要求确认。
- 一次用户意图产生的持久化变更，最多要求一次明确确认。
- CLI、MCP、HTTP 以及未来 WebUI/GUI 使用相同的流程语义。
- 简化交互不得绕过写入前复核、陈旧计划检测、恢复和人工修改保护。

## UX-001 — 缩短 Hash 的默认展示

### 问题

CLI、Agent 回复或其他人类界面直接展示完整 SHA-256 时，来源版本难以快速识别，多个版本也不易比较。

### 目标体验

完整 SHA-256 继续作为来源版本的规范身份，用于对象路径、来源 URI、持久化记录、完整性校验和机器可读协议。CLI、日志摘要、Agent 回复以及未来 WebUI/GUI 默认显示前 12 个十六进制字符，并提供查看或复制完整值的方式。

短 Hash 只是展示形式，不得写回规范身份字段，也不得单独用于完整性判断。若未来允许用户输入 Hash 前缀，前缀必须在当前 Vault 中唯一；存在歧义时拒绝操作并显示候选项。

### 验收标准

- 默认人类可读输出不再以 64 字符 Hash 作为主要标识。
- JSON、来源 URI、对象存储和持久化元数据仍保留完整 SHA-256。
- 详细视图可以获得完整值。
- 相同前缀对应多个对象时，不会静默选择其中一个。

## UX-002 — 每次写入只确认一次

### 问题

写笔记、审阅变化、保存和查询由 Agent 串联时，用户可能在多个只读步骤之间反复确认。确认次数与命令次数绑定，掩盖了真正需要授权的持久化写入。

### 目标体验

Agent 自动完成定位 Vault、读取配置、查询、review、生成计划和展示摘要。只有即将执行会修改 Vault 或宿主文件的 operation 时，Agent 才请求一次明确确认。用户拒绝或计划内容发生变化后，不执行写入；计划失效时展示变化并重新请求确认。

用户直接运行 `kb apply <operation-id>` 已经明确指定写入动作，CLI 不再增加第二层交互确认。MCP、HTTP 和未来 WebUI/GUI 可以采用各自的确认控件，但一次 operation 的最终写入只形成一个确认点。

### 验收标准

- `query`、`status`、`lint`、`review`、计划创建和 operation 查看不要求确认。
- Agent 可以连续执行完成任务所需的只读步骤。
- 写入前向用户展示 operation ID、变更摘要和受影响路径。
- 内容未变化时，一个 operation 最多请求一次确认。
- 确认后不再逐文件或逐内部步骤询问。
- 写入范围变化、计划失效或发生冲突时，原确认不延伸到新计划。

## UX-003 — 缩短并澄清核心流程

查询是随时可用的读取能力，不是写笔记或入库后的强制步骤。核心体验分为三个独立路径。

### 保存来源笔记

```text
写入已准入的主题目录
        ↓
自动检查变化并生成保存预览
        ↓
用户确认一次
        ↓
保存来源版本
```

Agent 面向用户描述“发现了什么变化”和“将保存什么”，无需暴露每个内部命令。CLI 仍可保留 `review`、`operation show` 和 `apply` 作为可组合的底层能力；后续可以增加组合入口，但命令名称和参数需在实现前单独设计。

### 查询知识

```text
输入问题 → 查询 Wiki、来源或两者 → 返回结果与精确引用
```

查询不依赖刚刚执行过 review、apply 或索引重建。可选索引不可用时遵循既有回退规则，不向用户增加确认步骤。

### 整理并保存知识

```text
查询并读取资料
        ↓
生成 research/article 变更预览
        ↓
用户确认一次
        ↓
保存知识及派生的 index/log 更新
```

一个知识 operation 中的正文、引用、index 和 log 是同一次写入，不分别确认。

### 验收标准

- 用户可以从“写笔记”“查询”和“整理知识”任一入口开始，不必记住一条统一的长流程。
- Agent 默认用用户任务描述流程，不逐条复述内部命令。
- 来源保存和知识保存都遵循“预览一次、确认一次、保存一次”。
- 查询路径不产生写入，也不要求确认。
- CLI、MCP、HTTP 和未来 WebUI/GUI 对 operation、预览、确认和失效使用一致语义。

## UX-004 — 区分相关性检索与精确匹配

### 问题

BM25F 会把包含连字符的查询拆成多个词项，并返回命中任一词项的相关结果。例如查询完整标识 `kb-incremental-rebuild-probe` 时，不包含该完整标识、只包含 `probe` 的文档也可能进入结果。该行为适合发现相关内容，但不能证明某个完整名称、ID 或短语确实存在。

Direct 与 BM25F 的匹配方式不同，也增加了用户判断查询结果的成本。当前入口没有明确区分“发现相关内容”和“验证精确文本”。

### 目标体验

默认查询继续用于相关性检索。CLI、MCP、HTTP 以及未来 WebUI/GUI 还应提供明确的精确匹配能力，用于完整名称、ID、错误码和短语；具体命令名称、参数及 BM25F/Direct 的统一语义在实现前单独设计。

### 验收标准

- 用户能够明确选择相关性检索或精确匹配。
- 精确匹配不会仅因某个拆分词项命中而返回结果。
- 查询结果说明实际采用的匹配方式。
- BM25F 与 Direct 对精确匹配采用一致的用户可见语义。
- 精确匹配不要求确认，也不修改索引或 Vault。

## UX-005 — 明确区分 Vault 与机器目录诊断

### 问题

`kb doctor` 的 `standard_directories` 检查统计机器级 config、state 和 cache 目录。新环境中的目录尚未按需创建时，doctor 会报告 `0/3` 或 `2/3 standard directories currently exist` warning。该消息没有说明检查对象位于机器用户目录，容易被理解为 Vault 缺少主题目录、Wiki 目录或备份恢复不完整。

缺少尚未使用的机器级目录不影响通过显式路径打开、查询或校验 Vault，因此 warning 也可能让正常的首次运行看起来存在故障。

### 目标体验

doctor 应分别命名 Vault 结构检查与机器级运行目录检查，并说明缺失目录是否会按需创建、影响哪些功能以及是否需要用户处理。正常的惰性初始化状态不应使用与功能异常相同的警告表达。

### 验收标准

- `standard_directories` 的结果明确指出检查的是机器级 config、state 和 cache 目录。
- 每个缺失目录都说明用途、是否按需创建和实际影响。
- Vault 目录完整性由独立检查报告，不与机器目录计数混合。
- 新环境通过显式路径完成只读操作时，不显示无法采取行动的笼统 warning。
- CLI、MCP、HTTP 和未来 WebUI/GUI 使用同一组诊断事实和含义。

## UX-006 — 区分备份校验失败与恢复失败

**状态：** 已解决。归档校验失败使用 `backup_verification_failed`；`error.details.reason` 提供具体原因，`error.details.legacy_code` 在迁移期间提供 `restore_failed`。恢复目标与发布错误继续使用各自的稳定代码。

### 问题

此前，`kb backup verify` 发现 ZIP 条目与 `manifest.json` 不一致时返回稳定错误码 `restore_failed`。错误消息能够说明归档校验失败，但错误码把独立校验操作归类为恢复失败；自动化、MCP、HTTP 以及未来 WebUI/GUI 无法仅凭错误码区分“归档无效”和“恢复目标写入失败”。当前归档校验使用 `backup_verification_failed`，同时保留 `legacy_code: "restore_failed"` 作为迁移详情；旧客户端仍须显式升级以识别新错误码。

### 目标体验

备份错误码应区分归档读取或校验失败、恢复目标不符合要求，以及恢复发布或写入失败。调整稳定错误码需要先定义兼容策略，避免已有客户端在没有迁移说明的情况下失去错误处理分支。

### 验收标准

- `backup verify` 的归档校验失败不使用只表示恢复执行失败的错误码。
- `backup restore` 在归档校验、目标检查和恢复写入阶段返回可区分的错误类别。
- CLI、MCP、HTTP 和未来 WebUI/GUI 使用相同错误码与含义。
- 错误响应继续提供具体原因和可执行的 `next_action`。
- 错误码变更具有明确的客户端兼容与迁移说明。

## 非目标

- 不缩短或替换持久化的 SHA-256 身份。
- 不允许 Agent 在未获得最终写入确认时自动 apply。
- 不为查询增加确认或强制入库步骤。
- 不在问题定义阶段确定新的组合命令名称。
- 不在问题定义阶段确定精确匹配的命令名称或参数。
- 不取消陈旧计划检测、中断恢复、并发锁或人工修改保护。

## 后续实施顺序

1. 调整 Portable Agent Skill 的交互约束和回复格式，消除只读步骤之间的确认。
2. 统一 CLI、MCP 和 HTTP 的变更摘要，使各入口都能支持一次集中确认。
3. 设计来源保存与知识保存的组合入口，同时保留现有底层命令。
4. 将相同语义用于 WebUI 和 GUI，并完成真实端到端工作流验证。
