# 使用体验改进

本文档记录真实 Vault 使用中确认的产品体验改进及其状态。具体交互语义、兼容边界和 Skill 分发约定见[使用体验与 Agent Skill 套件设计](../superpowers/specs/2026-09-08-usable-agent-skills-design.md)；现有命令、文件格式和安全边界仍以 reference 与架构文档为准。

## 目标原则

- 机器身份保持精确、稳定；人类界面优先展示易识别的信息。
- 查询、检查和生成预览等只读操作不要求确认。
- 一次用户意图产生的持久化变更，最多要求一次明确确认。
- CLI、MCP、HTTP 以及未来 WebUI/GUI 使用相同的流程语义。
- 简化交互不得绕过写入前复核、陈旧计划检测、恢复和人工修改保护。

## UX-001 — 缩短 Hash 的默认展示

**状态：** 已解决。人类可读 CLI 默认展示独立 SHA-256 的前 12 位，`--full-hashes` 显示完整值；JSON、MCP、HTTP 与持久化身份保持完整。

### 问题

CLI、Agent 回复或其他人类界面直接展示完整 SHA-256 时，来源版本难以快速识别，多个版本也不易比较。

### 目标体验

完整 SHA-256 继续作为来源版本的规范身份，用于对象路径、来源 URI、持久化记录、完整性校验和机器可读协议。CLI、日志摘要、Agent 回复以及未来 WebUI/GUI 默认显示前 12 个十六进制字符，并提供查看或复制完整值的方式。

短 Hash 只是展示形式，不得写回规范身份字段，也不得单独用于完整性判断。若未来允许用户输入 Hash 前缀，前缀必须在当前 Vault 中唯一；存在歧义时拒绝操作并显示候选项。

### 验收标准

- 默认人类可读输出不再以 64 字符 Hash 作为主要标识。
- JSON、来源 URI、对象存储和持久化元数据仍保留完整 SHA-256。
- 详细视图可以获得完整值。
- 相同前缀对应多个对象时，不会静默选择其中一个。

## UX-002 — 每次写入只确认一次

**状态：** 已解决。只读与计划动作不要求确认；Agent 或 UI 在最终 apply 前展示一次 `operation_summary` 并取得授权，直接执行 `kb apply` 则是 CLI 用户的明确写入动作。

### 问题

写笔记、审阅变化、保存和查询由 Agent 串联时，用户可能在多个只读步骤之间反复确认。确认次数与命令次数绑定，掩盖了真正需要授权的持久化写入。

### 目标体验

Agent 自动完成定位 Vault、读取配置、查询、review、生成计划和展示摘要。只有即将执行会修改 Vault 或宿主文件的 operation 时，Agent 才请求一次明确确认。用户拒绝或计划内容发生变化后，不执行写入；计划失效时展示变化并重新请求确认。

用户直接运行 `kb apply <operation-id>` 已经明确指定写入动作，CLI 不再增加第二层交互确认。MCP、HTTP 和未来 WebUI/GUI 可以采用各自的确认控件，但一次 operation 的最终写入只形成一个确认点。

### 验收标准

- `query`、`status`、`lint`、`review`、计划创建和 operation 查看不要求确认。
- Agent 可以连续执行完成任务所需的只读步骤。
- 写入前向用户展示 operation ID、变更摘要和受影响路径。
- 内容未变化时，一个 operation 最多请求一次确认。
- 确认后不再逐文件或逐内部步骤询问。
- 写入范围变化、计划失效或发生冲突时，原确认不延伸到新计划。

## UX-003 — 缩短并澄清核心流程

**状态：** 已解决。`kb source save` 与 `kb knowledge save` 提供组合入口；默认准备摘要，`--confirm` 提交同一份已准备内容，`--yes` 用于调用前已经取得授权的单次执行。底层 `review`、`plan create`、`operation show` 和 `apply` 继续用于高级编排。

查询是随时可用的读取能力，不是写笔记或入库后的强制步骤。核心体验分为三个独立路径。

### 保存来源笔记

```text
写入已准入的主题目录
        ↓
自动检查变化并生成保存预览
        ↓
用户确认一次
        ↓
保存来源版本
```

Agent 面向用户描述“发现了什么变化”和“将保存什么”，无需暴露每个内部命令。CLI 使用 `kb source save` 完成该流程，并保留 `review`、`operation show` 和 `apply` 作为可组合的底层能力。

### 查询知识

```text
输入问题 → 查询 Wiki、来源或两者 → 返回结果与精确引用
```

查询不依赖刚刚执行过 review、apply 或索引重建。可选索引不可用时遵循既有回退规则，不向用户增加确认步骤。

### 整理并保存知识

```text
查询并读取资料
        ↓
生成 research/article 变更预览
        ↓
用户确认一次
        ↓
保存知识及派生的 index/log 更新
```

一个知识 operation 中的正文、引用、index 和 log 是同一次写入，不分别确认。

### 验收标准

- 用户可以从“写笔记”“查询”和“整理知识”任一入口开始，不必记住一条统一的长流程。
- Agent 默认用用户任务描述流程，不逐条复述内部命令。
- 来源保存和知识保存都遵循“预览一次、确认一次、保存一次”。
- 查询路径不产生写入，也不要求确认。
- CLI、MCP、HTTP 和未来 WebUI/GUI 对 operation、预览、确认和失效使用一致语义。

## UX-004 — 区分相关性检索与精确匹配

**状态：** 已解决。`kb query --exact` 与 MCP/HTTP 的 `match_mode: "exact"` 不分词、不读写 BM25F 缓存，并在响应中报告实际匹配方式。

### 问题

BM25F 会把包含连字符的查询拆成多个词项，并返回命中任一词项的相关结果。例如查询完整标识 `kb-incremental-rebuild-probe` 时，不包含该完整标识、只包含 `probe` 的文档也可能进入结果。该行为适合发现相关内容，但不能证明某个完整名称、ID 或短语确实存在。

Direct 与 BM25F 的匹配方式不同，也增加了用户判断查询结果的成本。现已通过 `--exact` 明确区分“发现相关内容”和“验证精确文本”。

### 目标体验

默认查询继续用于相关性检索。CLI 使用 `kb query --exact`，MCP/HTTP 使用 `match_mode: "exact"` 进行区分大小写的 Unicode 字面匹配；BM25F 与 Direct 共享该用户可见语义。

### 验收标准

- 用户能够明确选择相关性检索或精确匹配。
- 精确匹配不会仅因某个拆分词项命中而返回结果。
- 查询结果说明实际采用的匹配方式。
- BM25F 与 Direct 对精确匹配采用一致的用户可见语义。
- 精确匹配不要求确认，也不修改索引或 Vault。

## UX-005 — 明确区分 Vault 与机器目录诊断

**状态：** 已解决。`vault_structure` 报告选中 Vault 的必需路径，`machine_runtime_directories` 报告机器级 configuration、state 和 cache 目录；尚未创建的按需目录为 `pass`，既有但不可用的目录才报告问题。

### 问题

此前，`kb doctor` 的 `standard_directories` 检查统计机器级 config、state 和 cache 目录。新环境中的目录尚未按需创建时，doctor 会报告 `0/3` 或 `2/3 standard directories currently exist` warning。该消息没有说明检查对象位于机器用户目录，容易被理解为 Vault 缺少主题目录、Wiki 目录或备份恢复不完整。当前已由 `vault_structure` 与 `machine_runtime_directories` 两项独立检查替代。

缺少尚未使用的机器级目录不影响通过显式路径打开、查询或校验 Vault，因此 warning 也可能让正常的首次运行看起来存在故障。

### 目标体验

doctor 应分别命名 Vault 结构检查与机器级运行目录检查，并说明缺失目录是否会按需创建、影响哪些功能以及是否需要用户处理。正常的惰性初始化状态不应使用与功能异常相同的警告表达。

### 验收标准

- `vault_structure` 报告选中 Vault 的必需文件和目录，以及每个缺失或类型无效的 Vault 路径。
- `machine_runtime_directories` 报告机器级 configuration、state 和 cache 目录，说明它们按需创建；普通缺失为 `pass`，既有但无法检查、不是目录或权限不可用时才报告问题。
- Vault 目录完整性与机器运行目录由不同检查 ID 报告，不再混合为目录计数。
- 新环境通过显式路径完成只读操作时，未创建的机器运行目录不产生无法采取行动的笼统 warning。
- CLI、MCP、HTTP 和未来 WebUI/GUI 使用同一组诊断事实和含义。

## UX-006 — 区分备份校验失败与恢复失败

**状态：** 已解决。归档校验失败使用 `backup_verification_failed`；`error.details.reason` 提供具体原因，`error.details.legacy_code` 在迁移期间提供 `restore_failed`。恢复目标与发布错误继续使用各自的稳定代码。

### 问题

此前，`kb backup verify` 发现 ZIP 条目与 `manifest.json` 不一致时返回稳定错误码 `restore_failed`。错误消息能够说明归档校验失败，但错误码把独立校验操作归类为恢复失败；自动化、MCP、HTTP 以及未来 WebUI/GUI 无法仅凭错误码区分“归档无效”和“恢复目标写入失败”。当前归档校验使用 `backup_verification_failed`，同时保留 `legacy_code: "restore_failed"` 作为迁移详情；旧客户端仍须显式升级以识别新错误码。

### 目标体验

备份错误码应区分归档读取或校验失败、恢复目标不符合要求，以及恢复发布或写入失败。调整稳定错误码需要先定义兼容策略，避免已有客户端在没有迁移说明的情况下失去错误处理分支。

### 验收标准

- `backup verify` 的归档校验失败不使用只表示恢复执行失败的错误码。
- `backup restore` 在归档校验、目标检查和恢复写入阶段返回可区分的错误类别。
- CLI、MCP、HTTP 和未来 WebUI/GUI 使用相同错误码与含义。
- 错误响应继续提供具体原因和可执行的 `next_action`。
- 错误码变更具有明确的客户端兼容与迁移说明。

## UX-007 — 降低正式版本的安装成本

**状态：** 已实现，待随下一版本发布。正式发布流程同时生成三个可执行文件和三个完整归档，并将六个文件写入签名保护的 `SHA256SUMS`。一步安装入口仍未实现。

### 问题

用户必须自行判断 CPU 和操作系统、选择归档、校验下载、解压、找到内部程序、移动到一个位于 `PATH` 的目录，并在 Unix 平台确认执行权限。README 能说明这些步骤，但不能消除这些步骤。首次用户因此容易把“Release 已包含二进制程序”和“下载物可以直接执行”混为一谈，也容易退回源码工作区中的构建产物进行测试。

归档仍有实际作用：它把可执行文件、`LICENSE` 和 `INSTALL.md` 作为一个版本单元分发，并能保留 Unix 文件权限。仅在 Release 中额外上传裸 `kb` 文件不能完整解决安装问题，因为浏览器下载后仍可能缺少执行权限，也不会自动放入 `PATH`。

### 目标体验

保留可校验的跨平台归档作为手工安装和便携分发方式，同时提供受支持的一步安装入口。安装入口负责选择匹配的平台资产、校验 SHA-256 和发布签名、解压并安装到用户级可执行目录，最后运行 `kb version` 验证结果。Linux/macOS 与 Windows 使用各自原生可审阅的安装脚本；后续可以增加主流包管理器，但不能要求用户安装语言运行时才能获得基础 CLI。

### 验收标准

- README 的首选安装路径不要求用户手工选择归档、解压和移动文件。
- 安装过程默认写入用户级目录，不要求管理员权限，并明确报告目标路径。
- 安装前验证发布校验和与签名，失败时不替换已有 `kb`。
- Linux、macOS 和 Windows 都有等价的一步安装入口。
- 手工下载归档的方式继续可用，并明确说明归档内才包含可执行程序。
- 安装完成后，新终端可以直接运行 `kb version`。
- 源码构建、Cargo 安装和正式 Release 安装仍保持可区分的更新边界。

## UX-008 — 配置编辑沿用已有 YAML 风格

**状态：** 待解决。`kb config admission add` 能保留已有条目和配置语义，但在多行对象列表末尾追加了单行对象，导致同一份 `admission.yml` 出现两种书写风格。

### 问题

人工维护的准入条目使用多行格式时：

```yaml
- id: "research"
  path: "Research"
  enabled: true
```

CLI 新增条目当前可能写为：

```yaml
- { id: "plugin", path: "Plugin", enabled: true }
```

两种形式在 YAML 中含义相同，也能通过 schema 校验，但混合格式降低了人类阅读和继续手工编辑的连贯性。配置命令承诺保留无关字段、顺序和注释时，也应尽可能沿用目标列表的局部格式。

### 目标体验

`kb config admission add` 检测 `directories` 中已有条目的书写方式，并使用相同的块式或流式格式追加新条目。空列表首次新增时采用项目模板的规范块式格式。`enable`、`disable` 和其他配置编辑只修改目标值，不重排或重写无关条目。

### 验收标准

- 多行条目列表新增后仍全部保持多行格式。
- 单行条目列表新增后可以沿用单行格式。
- 从 `directories: []` 首次新增时采用规范的多行格式。
- 编辑继续保留注释、条目顺序、未知字段和未修改字段的引号形式。
- 无法安全保留现有格式时拒绝修改并给出明确说明，不静默格式化整份文件。
- CLI 修改后的文件仍通过 `kb config validate`。

## UX-009 — 知识库维护保持只读

**状态：** 部分解决。Agent Skill 已明确只读边界与动态汇总规则；CLI 尚无聚合维护命令。用户要求“维护”“体检”或“维护汇总”时，不应隐式执行来源入库、知识生成、operation apply 或缓存重建。

### 问题

“维护汇总”容易被 Agent 错误解释为“先保存全部来源，再生成一篇 Wiki 汇总”。这会把状态检查扩大成持久化写入，并错误地把一句维护请求视为多个内容变更的授权。维护与入库、知识整理是三个独立意图；即使维护发现待处理内容，也只能报告数量和范围。

当前 CLI 也缺少一个直接面向用户的聚合维护报告。`review`、`lint` 和 `doctor` 分别返回事实，但 `review` 在发现变化时还会准备一个操作计划，`lint` 不报告检查链接总数，`doctor` 不提供可直接展示的 `ok` 聚合字段。Agent 不得自行编造缺失统计或把所有独立诊断压成未经定义的健康分数。未来原生维护入口应能读取来源差异而不创建操作计划。

### 目标体验

维护默认执行只读巡检。摘要根据实际结果选取对用户有决策价值的信息：优先说明需要关注的来源变化、lint finding、诊断失败或未检查项；状态正常时只保留必要结论。没有返回的字段应省略，不要求固定版式、固定措辞或固定图标。发现问题时可链接或展开原始独立报告。任何入库、知识生成、修复或缓存重建都由用户随后明确提出。

### 验收标准

- “维护”“体检”和“维护汇总”不会调用 `kb source save`、`kb knowledge save` 或 `kb apply`。
- 来源变化来自准入目录检查；按响应中的新增、修改、删除、跳过或未变化等实际分类报告，不把所有变化笼统称为“待入库”。
- lint 与 doctor 保留各自语义，摘要中的每个数字都能追溯到实际响应字段。
- 响应不支持链接总数或整体 `ok` 时，界面明确省略，而不是推断或伪造。
- 发现来源变化时，只展示数量和必要路径摘要，不自动保存，也不自动生成确认流程。
- 原生维护入口检查来源变化时不创建可应用的操作计划；在该入口实现前，Agent 不向用户暴露 `review` 的内部计划，也不据此发起确认。
- 没有异常或没有对应数据时可省略分项，不用空字段凑成固定报告。
- CLI、Agent Skill、MCP、HTTP 和未来 WebUI/GUI 对维护的只读边界一致。

## UX-010 — Agent Skills 从格式合规升级为执行有效

**状态：** 待解决。当前 8 个 Skill 都满足 Agent Skills 的最小目录和 frontmatter 要求，但现有校验主要证明文件可被发现和安装，尚不能证明 Skill 会在正确任务中触发、按预期调用 `kb`，并在真实异常分支中给出可靠结果。

### 问题

[Agent Skills 规范](https://agentskills.io/specification)只要求每个 Skill 目录包含 `SKILL.md`；`scripts/`、`references/` 和 `assets/` 是按需使用的可选资源。因此，“只有 `SKILL.md`”本身不是缺陷，也不应为了目录齐全而添加空文件或重复实现 `kb` CLI。

当前实现仍停留在最小可用层：

- `description` 说明了功能范围，但没有经过正向、反向和相邻意图的触发测试；`kb-vault`、`kb-config`、`kb-connect` 和 `kb-ops` 等边界是否会误触发或漏触发尚未验证。
- 多数正文把完整流程压缩在一个段落中，正常路径、分支条件、失败处理和完成证据不够容易扫描。
- 所有 Skill 重复同一组安全规则，其中部分规则与只读 Skill 无关，既占用上下文，也可能削弱任务重点。
- Skill 明确依赖 Knowledge-Brain CLI 或 MCP，却没有用 `compatibility` 等信息表达运行条件；许可证和版本来源也没有形成可检查的分发元数据。
- 缺少基于真实用户请求的触发与输出质量评估。目前只能验证结构和安装结果，不能比较“使用 Skill”是否比“不使用 Skill”更准确、更短或更稳定。
- `kb skills install` 的内置资源模型当前只覆盖 `SKILL.md`。未来一旦按需增加 `references/`、`assets/` 或 `scripts/`，CLI 安装、升级、所有权检查和卸载必须能够完整处理嵌套资源。

### 目标体验

每个 Skill 保持一个清晰任务边界，`SKILL.md` 只承载每次触发都必须知道的步骤、默认选择和高价值陷阱。只有在真实执行表明详细说明、模板或确定性辅助逻辑能够改善结果时，才分别放入 `references/`、`assets/` 或 `scripts/`，并在正文中写明何时读取或运行。现有 `kb` 命令能够可靠完成的工作不再包装成重复脚本。

Skill 优化以执行证据为依据：先建立真实中文和英文用户请求，验证是否触发正确的专项 Skill；再从执行轨迹、最终输出、Vault 持久化状态和用户反馈中修订描述与正文。评估应包含相邻意图和不应触发的请求，避免只测试显式写出命令名称的理想样例。

### 验收标准

- 8 个 Skill 继续通过 Agent Skills 结构校验，名称与目录一致，描述包含功能和触发意图。
- 每个 Skill 有正向、反向和相邻意图样例，至少覆盖中文与英文表达，并记录触发结果。
- 代表性真实流程覆盖正常路径、空结果、无效输入、拒绝写入、陈旧确认或恢复等与该 Skill 相关的分支；结果通过外部状态验证，不只检查 Agent 的文字结论。
- `SKILL.md` 使用可扫描的步骤和条件分支；只保留该 Skill 必需的安全规则，公共规则由单一源生成或同步，避免人工漂移。
- 对确有运行要求的 Skill 补充可移植的兼容性说明；实验性的 `allowed-tools` 不作为跨 Agent 安全边界。
- 支持文件只在评估证明有价值时加入，并使用 Skill 根目录相对路径按需引用；不要求每个 Skill 拥有同样的目录结构。
- `kb skills install`、升级、状态检查和卸载能够处理完整 Skill 目录及嵌套文件；`npx skills add` 安装结果与仓库源目录一致。
- 在至少两个支持 Agent Skills 的宿主上进行代表性验证，未验证宿主不宣称兼容。

## UX-011 — 提供可直接交给 AI Agent 的完整操作指南

**状态：** 已解决。AI Agent 的基础使用路径由独立的[操作指南](../guides/agent-operations.md)定义，CLI 是必需依赖，MCP 和 Agent Skills 是可选接入方式。

### 问题

面向人的首次使用教程和按模块拆分的参考文档，不能替代 Agent 执行整项任务时需要的连续操作约束。如果执行过程不先确认实际入口和安装状态，Agent 可能把直接调用 CLI 描述成使用 Skill，把读取 Skill 源文件描述成已安装，或在测试中完全跳过 Skill/MCP 的安装与触发环节。

Agent 操作说明也不能只覆盖 Skills 或 MCP。即使两者都不存在，Agent 仍应能通过 CLI 完成 Vault 初始化、准入配置、来源保存、知识整理、查询、维护、备份、恢复和更新。

### 验收标准

- 文档可脱离当前对话直接交给任意 AI Agent，并以 CLI 作为完整主路径。
- MCP 和 Skills 明确标记为可选入口，不被描述成 Knowledge-Brain 的运行前提。
- Agent 在执行前确认 CLI、Vault 和实际使用入口，不猜测路径或安装状态。
- 初始化、写笔记、准入、来源保存、知识保存、查询和维护的语义保持分离。
- 维护不会隐式执行入库、Wiki 整理、修复或缓存重建。
- Agent 只有在确认 Skill 已安装且本次实际采用时，才声称通过 Skill 完成操作。
- 结果报告包含实际入口、版本、Vault、持久化变化、验证证据和未验证项。
- README 提供稳定入口，详细命令仍链接各自参考文档，不在操作指南中复制完整命令参考。

## 非目标

- 不缩短或替换持久化的 SHA-256 身份。
- 不允许 Agent 在未获得最终写入确认时自动 apply。
- 不为查询增加确认或强制入库步骤。
- 不在问题定义阶段确定新的组合命令名称。
- 不取消陈旧计划检测、中断恢复、并发锁或人工修改保护。
- 不为了看起来完整而给所有 Skill 添加空的 `scripts/`、`references/` 或 `assets/`。

## 实现结果

Portable Agent Skill 的交互约束已由八项 `kb-*` Skill 落地：只读动作不要求确认，创建计划与最终 apply 保持一次明确确认；`kb skills` 与 `npx skills add` 的文件所有权互不覆盖。

来源与知识的组合入口复用同一应用层语义，CLI、MCP 和 HTTP 均保留预览、确认、陈旧状态复核与恢复规则。WebUI 和 GUI 的界面实现单独列入[未来扩展](future-extensions.md)。
